## 01 - 最小 Agent：让模型自己决定调用工具

```powershell
cd C:\Users\17839\Desktop\ai-job-assistant

# 不需要 Key，用离线假模型看清整个循环
python examples\01_add_agent.py "3 加 5 等于多少" --mock

# 用真模型（需要先配好 .env 里的 LLM_API_KEY）
python examples\01_add_agent.py "3 加 5 等于多少"
```

### 它在演示什么

Agent 的全部秘密就是这 5 步，循环起来：

```
1. 把「工具说明书」(JSON Schema) + 用户问题 一起发给模型
2. 模型不直接回答，而是返回：我要调用 add(a=3, b=5)     ← 模型只"决定"，不算数
3. 你的代码真正执行 add(3, 5)，得到 8                    ← 真正算数的是代码
4. 把 8 作为 tool 消息发回给模型
5. 模型基于这个结果生成最终回答
```

### 三个刻意设计的地方（面试时可讲）

**① 模型负责决策，代码负责执行**
模型自己心算 `3+5` 也能对，但换成 `12345678 + 87654322` 就开始编答案。
工具调用的意义是**把不确定的部分交给确定性的代码**。

**② 工具出错时返回错误信息，而不是抛异常**
`execute_tool()` 捕获所有异常并返回 `{"error": "..."}`。
因为模型看到失败原因才有机会改参数重试；直接崩掉整个 Agent 就断了。
而且错误信息要写得**人能看懂**——写 `decimal.ConversionSyntax` 模型看不懂，
写成"参数必须是数字，实际收到 a='x'"它才知道该改什么。

**③ 用 Decimal 而不是直接 a + b**
`0.1 + 0.2 == 0.30000000000000004`（二进制浮点固有误差）。
模型发来的是十进制数，就该用十进制算。
**这说明工具自身的实现质量，一样决定 Agent 的输出质量。**

### max_steps 防护

```powershell
python examples\01_add_agent.py "1 加 1" --mock --max-steps 1
```
会报错退出。真实系统里必须有这个上限，否则模型一旦陷入"反复调用工具"，一次故障就能烧掉大量 token。

## 和项目主体的关系

这个例子是**裸实现**：单文件、没有重试、没有埋点、没有降级。

项目主体里的 `app/llm.py` 是它的**工程版**——同样的调用，但加了：
指数退避重试、token 与成本埋点、流式输出、错误分类（哪些值得重试、哪些立刻失败）。

先用这个例子理解"Agent 是什么"，再看 `app/llm.py` 理解"生产环境要多做什么"。
