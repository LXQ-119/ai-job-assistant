# AI 应用开发面试知识库（示例）

这份文档本身就是知识库的语料。简历里的项目用自己整理的面经做知识库，
面试时演示出来的效果会比用公开文档更真实。

## RAG 基本流程

RAG（检索增强生成）分两段：**建索引**和**查询**。

建索引阶段：读取文档 → 切块 → 向量化（可选）→ 存入索引。
查询阶段：把问题也做同样处理 → 检索出最相关的若干块 → 把块拼进提示词 → 让模型基于这些块回答。

一句话总结它解决什么问题：模型的知识停留在训练时刻，而 RAG 让它可以引用**你私有的、最新的**资料，同时因为答案有出处，幻觉会明显减少。

## 切块策略

切块（chunking）是最容易被忽略但影响最大的一步。常见做法有三层：

第一，按文档本身的结构切，比如 Markdown 标题，这样每个块天然是完整的小节。
第二，按段落累积到目标长度，尽量不要把一段话从中间截断。
第三，超长段落做硬切，并保留 overlap——overlap 的作用不是"多存点字"，而是保证跨块边界的语义在两侧都完整出现，避免正确答案正好落在切口上。

块太长会让检索变糊（一个块里混了好几个主题），太短又会丢掉上下文。
中文一般从 500 到 800 字起步，然后**用评测集去调**，而不是凭感觉定。

## 检索：BM25 与向量

BM25 是经典的关键词检索算法，它靠两个统计量打分：词频（TF）和逆文档频率（IDF）。
IDF 的含义是：一个词在越少的文档里出现，它的区分度就越高，权重也该越大，所以 IDF 让"出现越少"的词获得更高权重。

向量的思路完全不同：把文本映射成高维向量，用余弦相似度衡量语义接近程度。

两者各有盲区。BM25 擅长精确术语匹配——"function calling"、"P95"、"BM25" 这种词，语义模型反而容易糊掉；向量擅长语义近似——用户问"响应太慢"，文档里写的是"延迟高"，只有向量能连起来。

## 混合检索与 rerank

混合检索就是把两路结果融合，通常比单用任意一路都好。两个工程细节必须注意：

第一，BM25 分数是**无上界**的，而余弦相似度在 -1 到 1 之间。直接相加是错的，会用 BM25 压死向量分数。正确做法是各自先归一化（比如 min-max 拉到 0 到 1），再加权求和。

第二，融合权重 alpha 不该拍脑袋定，应该用评测集扫一遍，找出最优值——0 表示纯 BM25，1 表示纯向量。

rerank 是另一个思路：先用便宜的方法（BM25 或向量）粗排出候选，再用一个更强的模型（cross-encoder 或大模型）对候选精排。因为只对少量候选做精细计算，成本和延迟都可控。

## RAG 效果评测

不评测的 RAG 就是玄学。常用指标有三个：

**Hit@k**：正确答案所在的文档是否出现在前 k 条检索结果里。衡量"有没有捞到"。
**MRR**（平均倒数排名）：正确结果排在第几位的倒数的平均值。衡量"排得够不够靠前"。
**关键词覆盖率**：标准答案里的关键术语在检索内容或生成答案里出现了多少。衡量"捞得全不全"。

做法是准备一个评测集（问题 + 正确来源 + 必含关键词），跑脚本输出指标。
简历上写的"命中率从 62% 提升到 89%"，就是靠这个流程前后对比得出的。

## 幻觉抑制

幻觉往往不是能力问题，而是没给模型"说不知道"的选项。可用的手段：

一是提示词里明确"只依据参考资料回答"，并给出诚实的退路——资料不足时必须回答"没有提到"，绝对不许编造。
二是强制标注引用编号，让每个结论都能被用户核对。
三是在检索为空时直接返回固定话术，不要白白调用模型。
四是生成后用关键词覆盖率之类的指标做自动检查，异常结果打标复核。

## Agent 与 function calling

Agent 的核心是让模型能"动手"，而不只是"说话"。

function calling（工具调用）是机制：你把可用的工具用 JSON Schema 描述给模型，模型在需要时返回一个结构化的调用请求（工具名 + 参数），你的代码真正执行它，再把结果回传给模型继续推理。

几个工程要点：工具必须做参数校验，不能信任模型给的参数；工具失败要返回明确的错误信息让模型有机会改；必须有最大步数限制，否则模型可能陷入无意义的循环；有副作用的工具（下单、发邮件、删数据）最好加人工确认。

## 提示词工程

工程化的提示词设计有几个实用原则：

把"角色、任务、约束、输出格式"分开写清楚；约束要具体可执行（"不超过 300 字"比"简洁一些"有用）；给出边界情况的处理方式；对抽取类任务把 temperature 设成 0 保证可复现。

还有一个容易被忽略的点：要求模型输出 JSON 时，`json_mode` 只保证"是合法 JSON"，**不保证字段符合你的 schema**。所以必须用 Pydantic 校验，校验失败时把错误信息和模型的原始输出一起回传，让它修正重试。

## 成本控制

成本 = token 数 × 单价。可用的手段按性价比排序：

一是提示词缓存。把稳定不变的部分（系统提示、长文档）放在前面，命中前缀缓存后输入单价会低一个数量级。
二是控制输出长度，输出单价通常是输入的几倍。
三是检索条数 top_k 不要设太大，够用就行，多余的块只是烧钱。
四是在调用前先判断，比如知识库为空时直接返回，不要浪费一次调用。
五是记录每次调用的 token 和成本，按场景拆分。**不测量就无法优化。**

另外要注意模型的峰谷计价：非高峰时段单价是高峰的一半，批量任务可以安排到非高峰跑。

## 延迟优化与流式

用户感知的延迟和真实的端到端延迟不是一回事。

流式输出（SSE）是收益最大的一招：总耗时没变，但**首字延迟**从"等三秒"变成"半秒就开始出字"，体感差别巨大。
其次是并行：检索、模板渲染这些互不依赖的步骤可以并发执行。
再次是缓存：热门问题的答案可以缓存，直接跳过模型调用。
最后是缩短提示词：输入越短，prefill 越快。

指标上要盯 P95 而不是平均值——平均值会把少数很慢的请求藏起来，而用户恰恰只记得那几次卡顿。

## 常见面试追问

**问：为什么用 LangChain 而不是原生 SDK？**
先答原生实现让你理解每一步在做什么，再用框架提效。框架抽象掉细节的代价是出问题时不好定位——能讲清这一点，比会用框架本身更有说服力。

**问：你的 RAG 准确率多少，怎么测的？**
报指标 + 评测集规模 + 改进手段。"命中率从 62% 提升到 89%，评测集 50 条人工标注，改进手段是引入混合检索和 rerank"——这样答才算完整。

**问：什么时候该引入向量数据库？**
当数据量或并发真的成为瓶颈时。几千个块用纯 Python 暴力检索完全够用，过早引入只是增加部署负担。能说清"什么时候不该用"，说明你理解的是权衡而不是跟风。

**问：怎么防止成本失控？**
缓存 + 输出长度限制 + top_k 控制 + 调用前判断 + 按场景记录成本 + 预算告警。

**问：并发上不去怎么办？**
先确认瓶颈在哪：是模型侧限流、还是自己的同步代码阻塞。同步调用要放进线程池，不要阻塞事件循环；再加信号量控制并发度，配合指数退避重试。
